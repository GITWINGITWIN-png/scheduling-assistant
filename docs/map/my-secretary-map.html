คู่ที่มักสับสน

/chat/stream (NDJSON)vs/events/stream (SSE)

แชทเป็น POST ที่ไม่ต่อใหม่เอง (ต่อใหม่ = รัน agent ซ้ำ เขียนปฏิทินซ้ำ) · เหตุการณ์เป็น SSE ที่ต่อใหม่เอง (ต่อใหม่ = ได้สิ่งที่พลาดไป)

Claude (Pro)vsOllama

Claude คิดและเลือก tool ในแชท + เขียนสรุปเช้า (นับโควตา) · Ollama สกัดนัดจากอีเมล อย่างเดียว (ฟรี เนื้อหาไม่ออกนอกเครื่อง)

snapshot (cache.py)vsแคชในหน่วยความจำ

snapshot อยู่ใน SQLite รอดการรีสตาร์ต และบอกได้ว่าเก่าแค่ไหน · แคชใน gmail.py/classroom.py หายเมื่อ process ตาย (2 นาที / 5 นาที) — หน้า Academic ข้ามแคชนี้ แต่ nudges ใช้

หมุดจากเมลvsโปรเจกต์

อยู่หน้า Projects เหมือนกัน แต่หมุดอยู่ใน pinned_emails · planner, nudges และ list_projects อ่านแค่ projects — หมุดจึงไม่ถูกวางแผนหรือเตือน

Plan now (ปุ่ม)vsวางแผนในแชท

ปุ่มใช้ plan_blocks + ดูก่อนจอง ทีละโปรเจกต์ · แชทให้ Claude เลือกจาก free_slots แล้วจองทันที และรับเงื่อนไขภาษาคนได้ (เฉพาะเช้า · อย่าแตะโปรเจกต์ B)

สรุปเช้าvsnudges

nudges คำนวณสดทุกครั้ง ไม่ใช้ token · สรุปเช้า ใช้ Claude วันละครั้ง แล้วเก็บไว้ — กด Refresh = เรียก Claude ใหม่

deliveredvsพูดจบแล้ว

delivered_at ถูกตั้ง ตอนเบราว์เซอร์ได้รับ ไม่ใช่ตอนตัวละครพูดจบ — ปิดแท็บตอนคิวยังเหลือ บรรทัดที่เหลือจะไม่ถูกเล่าอีก

emotionvsgesture

emotion = สีหน้าค้างไว้ตลอดบรรทัด (ผสม expression ของ VRM) · gesture = ท่าครั้งเดียว แล้วกลับ idle — มาจากแท็ก <mood> อันเดียวกัน

tts.pyvslocal_llm.py

ทั้งคู่เป็น HTTP client ไปหา process ในเครื่องและมี ล็อกของตัวเอง · แยกกันเพราะ Kokoro ใช้ CPU ส่วน Ollama ใช้ GPU — ล็อกร่วมจะทำให้สแกนเมล 180 วินาทีบล็อกเสียงพูด

token.json (ส่วนตัว)vstoken_school.json

ส่วนตัว = ปฏิทิน + Gmail ใช้ร่วมกัน (scope รวม) · โรงเรียน = Classroom อย่างเดียว — OAuth client ตัวเดียว สองบัญชี

ประวัติบนจอแชทvsความจำของ agent

FloatingChat เก็บข้อความไว้บนจอ ทุกหน้า แต่แต่ละ turn เป็น query() ใหม่ — agent ไม่รู้ว่าเมื่อกี้คุยอะไร (Stage 7 วางแผนใช้ resume)

สแกนแบบกดปุ่ม (unread)vsสแกนรายวัน 07:10 (today)

ทั้งคู่ ปักหมุดเองและอาจสร้างนัด · แบบกดปุ่มรันสดทุกครั้งและ ไม่ประกาศ · แบบรายวันเก็บผลวันละครั้งและ emit ให้ตัวละครพูด

เสียง · ปาก

WAV → ซองปาก 3 ย่าน

ใหม่ใน M8ฟรี · ในเครื่อง

เสียงของตัวละคร: ขอ WAV จาก /tts แล้วเล่นผ่าน Web Audio พร้อมคำนวณ “ซองปาก” ล่วงหน้าทั้งประโยค

ทำงานอย่างไร

  • synthesize(text) → POST /tts → ArrayBuffer · ได้ 503 = ไม่มีเสียง → เงียบแล้วไปต่อ (ไม่ใช่ error)
  • buildVisemeEnvelope: แยก 3 ย่านด้วย low-pass 500 / 2000 Hz → RMS ทุก 1/60 วินาที → ปรับตามความดังของประโยคนั้น → เปิดเร็ว (0.6) ปิดช้า (0.15)
  • playWithEnvelope: เขียน [ou, aa, ih] ลง mouthRef ทุกเฟรม นำหน้าเสียง 3 เฟรม (~50 ms) เพราะปากจริงขยับก่อนเสียงออก

หน้าตา / โครงสร้าง

mouthRef เป็น ref ไม่ใช่ state — ถ้าเป็น state จะ re-render ทั้ง dashboard (รวม FullCalendar) 60 ครั้งต่อวินาที

จุดที่มักพลาด / ต้องรู้

  • ปากรูปเดียว ('aa') ทำให้ดูเหมือนปลา — 3 ย่านคือสิ่งที่ทำให้อ่านออกว่าเป็นคำพูด
  • AudioContext เกิดมาแบบ suspended จนกว่าจะมีการคลิก — มี listener กลางที่ resume ให้

อธิบายละเอียด

ซองปากของประโยคหนึ่ง (audio.ts)

  • แบ่งเสียงเป็นเฟรมละ 1/60 วินาที → ที่ 24 kHz = 400 sample ต่อเฟรม
  • ย่านต่ำ < 500 Hz → ou · ย่านกลาง 500–2000 Hz → aa · ย่านสูง > 2000 Hz → ih
  • RMS ต่อย่านต่อเฟรม → หารด้วยค่าสูงสุดของประโยค (ประโยคเบาก็ยังขยับปาก)
  • กรองไม่สมมาตร: เป้าสูงขึ้น → ขยับ 60% ของระยะ · ต่ำลง → 15% (ปากเปิดเร็ว ปิดช้า)
  • ตอนเล่น อ่านเฟรมล่วงหน้า 3 เฟรม = 3 × 1000/60 ≈ 50 ms

ภาพกระบวนการที่เกี่ยวข้อง: ทางของเสียง: ข้อความ → WAV → ปาก

คิวกลางของทุกอย่างที่ตัวละครจะพูด — คำตอบจากแชทและเหตุการณ์จาก backend ถูกแปลงเป็น Performance {text, emotion, gesture, speak} ก่อนเข้าคิว ร่างจึงไม่ต้องรู้ว่าแต่ละบรรทัดมาจากไหน

ทำงานอย่างไร

  • drain() เล่นทีละรายการ: speak → รอเสียงจบ · ไม่พูด → แสดงฟองไว้ 2.5 วินาที
  • บรรทัดที่เล่นพลาดไม่ทำให้คิวค้าง (try/catch ต่อบรรทัด)
  • React อ่านผ่าน useSyncExternalStore · ตัวนับ seq เพิ่มทุกบรรทัด → ท่าเดิมซ้ำก็เล่นใหม่ได้
  • ฟองคำพูดขึ้นเสมอ แม้ไม่มีเสียงหรือไม่มีร่าง · มี “+N more” เมื่อมีคิวรอ

หน้าตา / โครงสร้าง

store ระดับโมดูล (queue.ts) ไม่ใช่ useState — loop 60 Hz อ่านได้โดยไม่เจอ stale closure · Character.tsx ตั้ง runner

จุดที่มักพลาด / ต้องรู้

  • ทีละบรรทัดโดยตั้งใจ: ตอนเช้าที่เหตุการณ์มาเป็นชุด ตัวละครจะไม่พูดทับตัวเอง
  • เบราว์เซอร์ยังไม่อนุญาตเสียง (ยังไม่มีการคลิก) → บรรทัดแรกรอจนคุณคลิก และขึ้น “click anywhere to enable sound”

OAuth · token

google_auth.py · token ต่อบัญชี

สิทธิ์เข้า Google ต่อบัญชี: google_auth.py จัดการไฟล์ token บนดิสก์

ทำงานอย่างไร

  • get_credentials(account, scopes): personal → token.json · school → token_school.json
  • token ได้ scope ไม่ครบ → เปิดเบราว์เซอร์ขอ consent ใหม่ · หมดอายุ → refresh
  • โหลดด้วย scope รวม (ที่ขอ ∪ ที่เคยได้) → refresh แล้ว scope ของอีกฝั่งไม่หด
  • OAUTHLIB_RELAX_TOKEN_SCOPE + ตาราง scope ทดแทน (Google เปลี่ยนชื่อ scope ของ Classroom)

หน้าตา / โครงสร้าง

credentials.json (ตัวตนของแอป) + token*.json (สิทธิ์ของแต่ละบัญชี) — ถูก git-ignore ทั้งหมด

จุดที่มักพลาด / ต้องรู้

  • ห้าม commit .env · credentials.json · token*.json · *.db
  • .env.example ก็ถูก git-ignore ไปด้วย (อยู่ในหมวด secrets ของ .gitignore) — clone ใหม่จะทำตาม README ที่ให้ cp .env.example .env ไม่ได้
  • .env.example ยังไม่มีคีย์ OLLAMA_* และ TTS_*

อ่านต่อในโค้ด: backend/app/services/google_auth.py · .gitignore
